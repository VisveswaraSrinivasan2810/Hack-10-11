# CIVICLENS AI — MASTER BUILD SPECIFICATION

## 0. ROLE

You are an expert product engineer, AI engineer, UX designer, solution architect, GIS engineer, and hackathon product builder.

Build a complete working MVP named:

# CivicLens AI
### From Citizen Observation to Verified Resolution

The application must be visually impressive, technically credible, easy to demonstrate, and realistic for a hackathon.

Do NOT build a generic complaint-management CRUD application.

The fundamental innovation is:

> CivicLens converts fragmented citizen observations into verified, geographically deduplicated, dynamically prioritized civic incidents and tracks them until real-world resolution is independently verified.

The core philosophy is:

**Observation → Intelligence → Incident → Priority → Action → Proof → Learning**

Existing systems often operate like:

**Complaint → Ticket → Closed**

CivicLens must demonstrate why the first model is better.

---

# 1. PRODUCT OBJECTIVE

Citizens encounter civic infrastructure problems such as:

- potholes
- garbage accumulation
- water leakage
- sewage overflow
- broken streetlights
- damaged roads
- damaged footpaths
- fallen trees
- illegal dumping
- damaged public infrastructure

Citizens often do not know:

- whether someone already reported the issue
- which authority owns the issue
- how serious the issue is
- whether similar reports represent the same problem
- whether authorities acted on it
- whether a "closed" complaint was actually fixed
- whether the problem keeps recurring

Authorities face another problem:

They receive fragmented complaints rather than a clean representation of real-world incidents.

CivicLens must bridge this gap.

---

# 2. PRIMARY PRODUCT PRINCIPLE

Do NOT make `Report` the central domain object.

The central domain object must be:

`CivicIncident`

A citizen submits an `Observation`.

Multiple observations may belong to one CivicIncident.

Example:

```text
Observation A ─┐
Observation B ─┤
Observation C ─┼── Civic Incident CL-1027
Observation D ─┘
```

Four citizen reports do NOT necessarily mean four civic problems.

This distinction must appear throughout the architecture, database, APIs and UI.

# 6. NOVELTY 1 — CIVIC INCIDENT FINGERPRINT

Create a conceptual `CivicFingerprint`.

It represents the identity of a real-world civic issue.

Inputs:

- latitude
- longitude
- issue category
- observation timestamp
- visual similarity
- spatial proximity
- temporal proximity

For the hackathon MVP, keep the implementation deterministic and understandable.

Example score:

```text
SameIncidentScore =
    0.40 * spatialSimilarity
  + 0.30 * categorySimilarity
  + 0.20 * visualSimilarity
  + 0.10 * temporalSimilarity
```

All scores normalized from 0 to 1.

Interpretation:

```text
>= 0.85 → Very likely same incident
0.65-0.84 → Possible match; ask citizen
< 0.65 → Likely new incident
```

Do NOT silently merge uncertain incidents.

Always preserve human override.

# 7. EASY DUPLICATE DETECTION IMPLEMENTATION

Hackathon implementation should be simple.

Step 1:

Step 2:

Step 3:

Calculate geographic similarity.

Step 4:

If an image embedding service is available, calculate image similarity.

If not available, implement a replaceable mock/deterministic similarity provider.

Step 5:

Step 6:

Show top matches to citizen.

# 8. NOVELTY 2 — CIVIC PRIORITY SCORE

Implement a transparent dynamic priority score called:

# CPS — Civic Priority Score

Score range:

`0-100`

Suggested formula:

```text
CPS =
    Severity             * 0.25
  + CitizenEvidence      * 0.15
  + LocationRisk         * 0.20
  + IncidentAge          * 0.10
  + Exposure             * 0.15
  + Recurrence           * 0.15
```

Keep weights configurable.

Priority bands:

```text
0-29   LOW
30-49  MODERATE
50-69  HIGH
70-84  VERY HIGH
85-100 CRITICAL
```

Every incident page must explain WHY its score exists.

Example:

```text
CIVIC PRIORITY SCORE
89/100 — CRITICAL

Severity                 92
Citizen Evidence         80
Location Risk            98
Incident Age             40
Public Exposure          95
Recurrence               65

Why Critical?

• Dangerous road damage detected
• 7 independent observations
• Located near a school
• High public exposure
```

Avoid black-box scoring.
